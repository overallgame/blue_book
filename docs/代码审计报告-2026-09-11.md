### 若对外提供服务，最该先处理的三件事

> 以下三项是「服务暴露到公网之前」必须完成的，不是当前待办。当前状态下无需动手，理由见上一节。

1. **后端 JWT 密钥是仓库里公开的默认值**（P0-1）。`deploy/blue-book.service` 没有 `EnvironmentFile`，因此按文档部署时生产环境用的就是 `default-jwt-secret-change-in-production`。任何读过仓库的人都能签发 `sub=<任意用户ID>` 的合法 token。这不是"配置不当"，而是认证体系失效。
2. **验证码体系整体失效**（P0-2 + P1-3 + P1-4）。`/api/v2/auth/code` 把验证码明文放进响应体，登录接口在手机号不存在时会提前返回（可枚举账号），注册接口对验证码没有尝试次数限制。三者组合起来 = 拿到任意手机号 → 读验证码 → 注册该号码的账号。
3. **评论接口未鉴权**（P0-3）。`POST /api/v1/comments` 同时在 `SecurityConfig` 的 `permitAll` 和 `JwtAuthFilter.PUBLIC_PATHS` 中，落库时 `userId = 0`，并且会给视频作者发一条站内通知。这是一个无需登录的、无频率限制的内容写入 + 通知注入原语。

Android 侧最严重的是**登录密码与 token 以明文 HTTP 传输**（按你的要求本次仅在报告中记录，见 P0-4）与**完整的请求/响应 body 被无条件写入 logcat**（P0-5、P0-6），后者在 release 未混淆（P2-A1）的前提下会原样进入发行包。

## 二、P0 严重（6 项）

### P0-1　后端：JWT 签名密钥使用仓库内公开的默认值，认证可被完全绕过

**位置**
- `backend/src/main/resources/application.yml:41`
- `backend/src/main/kotlin/com/example/bluebook/common/JwtUtil.kt:16-18`
- `deploy/blue-book.service:8`

**证据**

```yaml
# application.yml:41
app:
  jwt:
    secret: ${JWT_SECRET:default-jwt-secret-change-in-production}
```

```kotlin
// JwtUtil.kt:16-18
private val key: SecretKey = Keys.hmacShaKeyFor(secret.toByteArray().let { bytes ->
    if (bytes.size < 32) bytes + ByteArray(32 - bytes.size) { 0 } else bytes
})
```

```ini
# deploy/blue-book.service:8 —— 无 EnvironmentFile，无 JWT_SECRET / DB_PASSWORD / RABBITMQ_*
ExecStart=/usr/bin/java -Xmx2g -Xms2g -jar backend.jar
```

**影响**
密钥字面量在仓库中。任何人可离线用同一密钥签发 `HS256` token，把 `sub` 设成任意用户 ID（`JwtUtil.generateAccessToken` 只用 `sub` 和 `phone` 定位身份，见 `JwtAuthFilter.kt:40` 的 `setAuth(jwtUtil.getUserId(token))`），即**无需账号即可冒充任意用户**。

第二层问题：`JwtUtil` 的零填充把短密钥补成合法的 32 字节 HMAC 密钥，这恰好绕过了 jjwt 自身的 `WeakKeyException` 弱密钥保护。于是运维即使设置了 `JWT_SECRET=abc`，密钥也变成"3 个已知字节 + 29 个 0x00"，仍可被系统性推导。

**修复**
启动时校验：`JWT_SECRET` 缺失或等于默认值时直接 `fail fast` 拒绝启动；删除零填充逻辑，改为 `require(bytes.size >= 32)`；在 systemd unit 中用 `EnvironmentFile=/etc/blue-book/env` 注入真实密钥。

### P0-2　后端：`/api/v2/auth/code` 把短信验证码明文返回给任意调用者

**位置**：`backend/src/main/kotlin/com/example/bluebook/auth/service/AuthService.kt:63-72`、`auth/controller/AuthController.kt:25-27`

**证据**

```kotlin
// AuthService.kt:63-72
fun sendCode(request: SendCodeRequest): String {
    val phoneKey = "sms:phone:${request.phone}"
    if (redisTemplate.opsForValue().get(phoneKey) != null)
        throw SmsRateLimitException()

    val code = "%06d".format((Math.random() * 1000000).toInt())
    redisTemplate.opsForValue().set("sms:${request.phone}", code, Duration.ofMinutes(5))
    redisTemplate.opsForValue().set(phoneKey, "1", Duration.ofSeconds(60))
    return code // Return code in dev mode for testing convenience
}
```

`AuthController` 直接 `ApiResponse.ok(authService.sendCode(request))`，把 `code` 放进响应体。**没有任何 `@Profile` 或 debug 开关把它限定在开发环境。**

**影响**
手机号验证对 API 层面等于不存在。攻击者用受害者手机号调用 `/api/v2/auth/code`，从 JSON 响应里读到验证码，再调用 `/api/v2/auth/register` 完成注册，从而**抢占该手机号在该平台的账号身份**（受害者日后无法用自己号码注册/找回）。

另外 `Math.random()` 是 48 位 LCG，验证码不具备密码学随机性，可预测。

**修复**
永不返回验证码（仅在无短信通道的 `dev` profile 下打日志）；生成改用 `SecureRandom`；加每 IP / 每设备节流与验证码尝试计数。

> ⚠️ **按你的决定，本项本次不修改，仅作为已知风险记录。**

**位置**
- `core-network/build.gradle.kts:15`

**证据**

```kotlin

buildConfigField("String", "BASE_URL", "\"http://192.168.17.128:8080/\"")
```

```xml

```

`deploy/nginx.conf` 实际上已经配好了 TLS（`:10-12` 监听 443 并挂 Let's Encrypt 证书，`:4-8` 把 80 端口 301 跳转到 https）。也就是说服务端准备好了 HTTPS，但客户端默认直连 Spring Boot 的 8080 端口明文端口，绕过了 nginx。`network_security_config.xml` 里也没有任何 `<pin-set>` 证书固定，其白名单域名（`8.138.41.189`、`10.0.2.2`）甚至不包含实际使用的 `192.168.17.128`。

### P1-2　后端：分片上传接口完全没有归属校验，可向他人上传会话注入分片

### P1-6　Android：`TokenHolder` 持久化存在竞态，登出可能被在途写入覆盖

**位置**：`core-network/src/main/java/com/example/blue_book/network/TokenHolder.kt:27, 58-83`

**证据**

```kotlin
private val scope = CoroutineScope(SupervisorJob() + Dispatchers.IO)   // :27 无界 IO 线程池

    authToken = token
    scope.launch { dataStore.putString("auth_token", token) }          // :60 即发即忘
}

fun clear() {
    cleared = true
    authToken = null; refreshToken = null; phone = null
    scope.launch {

        dataStore.remove("phone")
    }
}
```

**影响**

**修复**
把所有持久化串行化到单线程上下文（`Dispatchers.IO.limitedParallelism(1)` 或 `Mutex`）；`saveAuthToken` 内先判断 `cleared`，若已登出则丢弃写入；token 对在同一次 `edit {}` 中落盘。

### Android 核心层（7 项）

- **P3-A1　`ApiGateway` 吞掉取消 + 每次请求重建 Retrofit**：`ApiGateway.kt:181-183` 的 `catch (e: CancellationException) { return }` 把取消吸收了（调用方继续执行）；`:117-124` 的 `private val retrofit: Retrofit get() = Retrofit.Builder()...build()` 每次 `createApi` 都新建一个 Retrofit；`okHttpClient!!` 是非 volatile 的 `var`，在 `refreshOkHttpClient()`（`:75-91`）写入的同时可能有请求在飞。建议：取消要重新抛出、每个 client 只构建一次 Retrofit、字段标注 `@Volatile`。

### 业务层（6 项）

## 七、待确认项（需运行环境才能定论，不作为结论）
