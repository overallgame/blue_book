## 一、需求梳理

### 1.1 已定的决策

| # | 决策 | 含义 |

### 1.3 需求条目（可验收）

- R1 相机实时识别二维码；识别到**站内码**时向后端校验后跳转
- R2 从相册选图识别，与实时识别走**同一套**解析与跳转逻辑
- R3 支持的码类型：视频、用户
- R4 非站内码：**不自动跳转**，展示内容并「复制」；http(s) 额外提供「用浏览器打开」
- R5 校验失败停在扫码页给出**具体原因**（码失效/内容不存在/无权查看/网络失败）
- R6 相机权限被拒时降级为「去设置」+「从相册选图」，不出现死页面
- R7 分享视频/用户时产出可被扫一扫识别的链接（与 R1–R3 同一套格式）
- R8–R10 扫码登录（**暂缓**，见第八节）

### 1.4 明确不做

一维码/条码；「我的二维码」；识图/扫物；**深链唤起**（浏览器点链接拉起 App——需 App Links 校验，且现在也没有网页端）；扫码登录的网页端。

## 二、需求分析：把「功能需求」和「非功能需求」分开

这一节是设计的**依据**，不是套话。后面所有的架构决定都能在这里找到出处。

### 2.1 为什么要分开

> **功能需求决定你做多少个页面；非功能需求决定你的架构长什么样。**

扫一扫的"功能需求"极其简单——**一句话就能说完**：扫个码，跳到对应内容。
但它的"非功能需求"一列出来，架构的形状立刻就被限定了。**如果只盯着功能需求设计，做出来会是一个"能扫码的相机页"，然后在真实使用中被权限、误扫、网络、失效码逐个击穿。**

### 2.2 功能需求 → 决定页面与入口

| 功能需求 | 决定的界面 |
|---|---|
| 扫码识别 | `ScanActivity`（相机预览页） |
| 相册识别 | 复用现成的 `IMAGE_PICKER`，**不新增页面** |
| 站内码跳转 | 复用现有的播放页 / 作者主页路由，**不新增页面** |
| 分享产出链接 | 改动播放页既有的分享逻辑，**不新增页面** |

**结论：只新增 1 个页面。** 功能需求层面这是个很小的功能——这也意味着**它的复杂度几乎全部来自非功能需求**。

### 2.3 非功能需求 → 决定架构（逐条映射）

| # | 非功能需求 | 它为什么是"非功能" | 它直接决定的架构 |
|---|---|---|---|
| N1 | **相机权限可能被拒** | 与"能不能扫"这个功能无关，是运行环境问题 | `ScanPhase.PermissionDenied(canAskAgain)` 必须是**一等状态**，而不是"没权限就 finish"；且相册路径成为必须（否则权限一拒功能就死） |
| N2 | **扫码输入完全不可信** | 任何人都能生成任意二维码 | 解析必须是**纯函数 + host 白名单**；外部链接**不自动打开**（R4）；解析与相机严格分离，才能穷举测试恶意输入 |
| N3 | **识别会失败、会误识别** | 相机是概率性输入设备 | 同码 2 秒去重；**先 resolve 成功再跳**（而不是扫到就跳）；`Resolving` 期间暂停分析器 |
| N4 | **相机是独占资源、耗电** | 与业务无关的资源约束 | `onPause` 必须释放相机；分析器要能独立于页面状态启停（`scanning` 与 `phase` 正交） |
| N5 | **码一旦流出去就改不得** | 分享出去的码生命周期远超部署地址 | 码里的 host 与 `BASE_URL` **解耦**（见 4.1）；编解码**单一定义**在 lib-base；解析白名单只加不删 |
| N6 | **识别库和后端格式都可能变** | 可维护性 | `BarcodeScanner` 接口化（换库改 1 个文件）；`resolve` 传**原始字符串**而不是解析后的字段（让服务端当唯一裁判） |
| N7 | **必须能被验证** | 可测试性 | 解析逻辑做成纯函数（相机代码永远测不了，所以必须把可测的部分切出来） |
| N8 | **网络随时可能失败** | 可用性 | 失败矩阵 11 行逐条定义；**网络失败时保留已扫到的内容**（`pendingPayload`），不让用户重扫一遍 |

### 2.4 结论：这个功能的"灵魂"是什么

类比"云笔记的灵魂不是笔记而是同步"——

> **扫一扫的灵魂不是「相机」，是「把不可信输入转换成可信动作」的那一步。**

相机只是输入设备，换成 ML Kit / ZXing / 系统相机都行，是**可替换的实现细节**。
真正决定这个功能质量的是三件事：

1. **什么算合法码**（N2 → 解析器 = 安全边界）
2. **扫到了该做什么、什么时候不该跳**（N3 → 先校验再跳）
3. **失败时用户看得懂吗、有出路吗**（N1/N8 → 降级路径 + 失败矩阵）

所以后面设计的重心全部落在这三处，而**不是**在相机预览的代码上——相机那部分只要"能用、不泄漏、能释放"就够了。

## 四、怎么拆（设计重点）

### 4.0 总原则：按"变化的原因"拆，不按"文件类型"拆

判断两个东西该不该分开放的**唯一标准**：它们会不会因为**不同的原因**而变化。

如果"换个识别库"和"后端改个 URL 路径"会让同一个文件两次被修改，这两件事就不该待在同一个文件里——变化节奏不同，一个的技术债会污染另一个。

扫一扫剥开是 **5 个独立变化的关注点**，后面所有模块/包/接口拆分都是这 5 条的投影：

| # | 关注点 | 它的变化原因 | 拆到哪 | 没拆开会怎样 |
|---|---|---|---|---|
| C1 | 相机预览与生命周期 | 换 CameraX/Camera2、省电策略 | `feature-scan/ui/scan/`（宿主内） | 相机代码与业务缠绕，业务没法单测 |
| C2 | 条码解码 | 换库、加一维码、调参数 | `BarcodeScanner` 接口 + 1 个实现 | 换库要动 ViewModel；识别率问题与业务问题混在同一个堆栈 |
| C3 | **码格式解析（安全边界）** | 后端格式变更 | **`lib-base/scan/`** | 见 4.1 |
| C4 | 业务决策（扫到什么做什么） | 产品规则变更 | `feature-scan/domain/` | 安全判据被产品改动误伤 |
| C5 | 内容校验与跳转 | 接口变更、路由变更 | `feature-scan/data/` + `ui/` | 网络细节漏进 UI |

### 4.1 必须提前定的拆分决定：码格式下沉 lib-base，且 host 与部署地址解耦

**第一半：为什么下沉 lib-base（而不是留在 feature-scan）**

站内码有两个**不同模块的消费方**：生成方是 `feature-video` 的分享按钮（R7），解析方是 `feature-scan`。
各自实现必然漂移。而这个项目**已经被同类问题咬过三次**：

- 主题色板：6 个模块各存一份，`feature-message` 的值与 app 差一个色阶且**静默失效**
- 样式：3 个模块各一份，靠"两处内容必须相同"的注释**人手同步**
- `default_avatar`：3 份，其中一份是**完全不同的图**

**码格式比它们更危险**：色板漂移是"颜色不对"，码格式漂移是"**自己分享出去的码自己扫不出来**"——而且只有真机上扫了才会发现。

所以编解码整体放 `lib-base/scan/ScanCodeFormat.kt`，与 `RoutePath`、`ExtraKeys` 并列。**这是一致性而非新发明**：lib-base 本来就是"跨模块字符串契约"的家。

**第二半：host 不能取 `BASE_URL`（本轮侦察的关键修正）**

侦察发现 `ApiGateway.BASE_URL = "http://192.168.17.128:8080/"`。三条问题：

1. **它是私有网段 IP**（RFC 1918）：把它印进二维码等于把内网拓扑发出去，且任何外部设备扫到都是死链
2. **它会变**：换虚拟机、换局域网、换端口都会变——而码是**会离开设备**的东西（分享到微信等），生命周期比部署地址长得多
3. **它是明文 HTTP**：与"对外可分享的正式链接"这个语义不符

按 4.0 的原则，这正好是两类不同的东西：

| | 性质 | 变化频率 | 该放哪 |
|---|---|---|---|
| **码里的 host** | **契约**（用户手里有实物） | 几乎不变，变了就是灾难 | 独立常量 + 解析白名单 |
| **`BASE_URL`** | **实现细节**（部署地址） | 换环境就变 | BuildConfig |

**设计**：

```kotlin
// lib-base/scan/ScanCodeFormat.kt —— 纯函数，无 Android/网络依赖
object ScanCodeFormat {
    /** 码里使用的 host：与部署地址解耦的「码域名」 */
    const val CODE_HOST = "bluebook.invalid"

    /** 解析时接受的 host 白名单：**只加不删**，这样换域名后老码继续有效 */
    private val ACCEPTED_HOSTS = listOf(CODE_HOST)

    fun videoUrl(aid: Long): String   // https://bluebook.invalid/v/{aid}
    fun userUrl(id: Long): String     // https://bluebook.invalid/u/{id}
    fun parse(payload: String): ScanTarget
}
```

- 本期 `CODE_HOST` 用 **RFC 2606 保留的 `.invalid` 顶级域**：它**保证永不解析**，因此
  ① 不会被别人抢注后拿来服务恶意内容 ② 不会让人误以为"点了能打开"。
  等你有了真域名，把 `CODE_HOST` 换掉、并把新域名**追加**进 `ACCEPTED_HOSTS`，**已发出的老码继续有效**。
- 解析**只认 `ACCEPTED_HOSTS`**，不看 `BASE_URL`。这样"码格式"和"部署地址"两个变化原因被彻底隔离。

**代价（如实说明）**：外部扫码器扫到会显示"打不开"。这是 P1（无网页端）的必然结果，不是设计缺陷；
将来上线分享页，把域名指过去即可，**码本身不用重新生成**——这正是把 host 独立出来的收益。

### 4.4 拆接口：区分"稳定契约"与"易变实现"

拆分最终落在接口上。**先明确一件事：不是所有东西都该抽象。** 这个功能里有两类接口，稳定度完全不同：

| 接口 | 稳定度 | 变化时改几个文件 | 放哪 |
|---|---|---|---|
| `ScanCodeFormat`（object，非 interface） | **最稳**：编码"我们和用户之间的契约"，码一旦流出就不能随便改 | 1 | lib-base |
| `ScanApi`（Retrofit） | 稳：HTTP 契约 | 1 | feature-scan/data |
| `ScanRepository`（interface） | 稳：给 ViewModel 的抽象 | 1~2 | feature-scan/data |
| `BarcodeScanner`（interface） | **易变**：识别库、参数、一维码 | **1**（只换实现） | feature-scan/ui |

**`BarcodeScanner` 接口化是本方案最便宜的一处投资**：

```kotlin
interface BarcodeScanner {
    /** 从一帧里解出所有二维码内容；无码返回空列表 */
    suspend fun analyze(image: ImageProxy): List<String>
    /** 从一张位图里解出（相册路径共用） */
    suspend fun analyze(bitmap: Bitmap): List<String>
    fun close()
}
```

三个价值：换库只改一个文件；相机路径与相册路径**共用它**（否则早晚出现"相机严、相册松"的漏洞）；
解析层完全不碰它，**所以"它不能被单测"不会拖累可测覆盖率**。

**反过来，不该抽象的地方要忍住**：不给 `ScanActivity` 抽接口、不给权限流程抽接口——它们只被系统调用，抽了也没人替换。这是另一种过度设计。

**用 4 条标准审视本功能的接口**（这 4 条来自另一篇方法论，逐条对照）：

| 标准 | 本功能怎么落实 | 反例（本可以写成但没写） |
|---|---|---|
| **少而稳** | `ScanRepository` 只有 1~2 个方法；`BarcodeScanner` 2 个。**只加不改**：`ACCEPTED_HOSTS` 用列表追加而不是替换 | 做一个 `ScanManager` 把相机/解析/网络/跳转全塞进去，7、8 个方法 |
| **语义清晰** | `ScanCodeFormat.parse(payload)`、`ScanTarget.InternalCode`；看名字就知道输入是不可信原始串 | `ScanCodeFormat.check(String): Any?` |
| **不泄露实现** | ViewModel 只依赖 `ScanRepository` 接口；`Result<ScanResolveDto>` 不出 data 层；**`resolve` 传原始字符串而非解析后的 id**——否则等于把"什么算站内码"这个判据泄露给客户端 | ViewModel 直接依赖 `ScanRemoteDataSource`；把 `ScanResolveDto` 透传到 UI |
| **类型安全** | 用 sealed `ScanTarget` 而不是 `String type` + nullable 字段 | `parse(): Pair<String, Long?>?` |

### 4.5 拆任务（逐步可验证）

| 步 | 内容 | 完成能验证什么 | 为什么排这里 |
|---|---|---|---|
| 1 | `feature-scan` 骨架 + 路由 + `:app` 依赖；入口改成跳路由，页面先空白 | 真机能进能返回 | 先单独验"模块接通"，后面能排除"是不是没接上" |
| 2 | **`ScanCodeFormat` + 单测**（含恶意/畸形输入） | 测试全绿，**不碰相机** | 安全边界先钉死，见下 |
| 3 | 相机预览 + `BarcodeScanner` + 去重；结果先打日志 | 真机扫出内容 | 不可测部分隔离在此步之后 |
| 4 | 后端 `/scan/resolve` + data 层 | curl + 真机各一次 | 契约先在后端定死 |
| 5 | 状态机与全部失败路径（7.2 逐行） | 逐条手动复现 | 失败路径是需求，不是收尾 |
| 6 | 相册识别（复用 `IMAGE_PICKER`） | 与相机路径结果一致 | 复用现成契约，风险低 |
| 7 | 分享升级成链接（R7），扫自己分享的码 | **端到端闭环** | 不做这步功能是空壳 |

**第 2 步刻意排在相机之前**，四个理由：

1. `ScanCodeFormat` 处理的是**完全不可信的外部数据**，它是安全边界
2. 它是**纯函数**，能在纯 JVM 上测——相机代码永远测不了
3. 如果先写相机，解析会被"顺手塞进"分析器回调，安全判断与相机代码缠在一起，再拆就贵了
4. 它**零风险**：不依赖相机、后端、权限，可以立刻开始

### 4.6 拆分自检（用项目已有标准验收）

| 检查 | 期望 | 手段 |

## 五、数据类设计

### 5.1 原则：把「隐性需求」变成「显式字段」

数据类的形状不是"把用到的字段列出来"，而是**回答"哪些状态是系统必须知道的"**。
判断标准：**如果某个状态的不同取值会导致不同的行为，它就必须是一个显式字段（最好是 sealed），而不是靠几个布尔/nullable 拼出来的组合。**

扫一扫有 4 个隐性需求需要显式化：

| 隐性需求 | 显式化为什么重要 |
|---|---|
| "这次失败是**哪种**失败" | 不同失败对应**不同出路**：去设置 / 重试 / 重选图 / 只提示。用 `Boolean` 表达不出来 |
| "扫到的码是**哪一类**" | 不同类走完全不同的流程：网络校验 / 直接展示 / 二次确认 |
| "当前处于**哪个阶段**" | 相机该不该开、按钮该不该显示，都由它决定 |
| "已扫到但**还没处理**的原文" | 网络失败时不能丢，否则用户要重扫一遍 |

### 5.2 反面写法（先说错的，才知道对的为什么对）

```kotlin
// ❌ 隐性需求没显式化：字段齐全，但语义全靠约定
data class ScanUiState(
    val isScanning: Boolean = true,
    val isResolving: Boolean = false,
    val hasError: Boolean = false,
    val errorMessage: String? = null,
    val targetType: String? = null,     // "VIDEO" / "USER"
    val targetId: Long? = null,
    val url: String? = null,
    val ticket: String? = null,
)
```

四个具体问题：

1. **非法组合可以被构造**：`isScanning && isResolving` 同时为 true、`targetType="VIDEO"` 而 `targetId=null`——编译器都不管，靠自觉
2. **`errorMessage` 有了，但不知道该给什么出路**：是"去设置"还是"重试"还是"重选图"？只能靠字符串猜或再补一个 `errorKind` 字段
3. **新增码类型要改所有使用点**：加"登录码"要加 `ticket` 字段并在每个 `if` 里补分支，编译器不会提醒你漏了
4. **`when` 无法穷举**：`targetType` 是 `String`，新增取值时编译器不报错——这正是线上 bug 的温床

### 5.3 正确写法：sealed 表达"互斥且穷举"的状态

```kotlin
// ScanContract.kt —— UDF 三件套里的 State

data class ScanUiState(
    /** 当前阶段：互斥，且 UI 的 when 必须穷举 */
    val phase: ScanPhase = ScanPhase.CheckingPermission,
    /** 已扫到、待处理的原文；网络失败时保留，用户不必重扫 */
    val pendingPayload: String? = null,
    /** 失败原因；sealed，每个分支就是一条出路 */
    val error: ScanError? = null,
    /** 分析器是否在跑。与 phase 正交：Resolving 时要暂停它 */
    val analyzing: Boolean = true,
)

sealed interface ScanPhase {
    data object CheckingPermission : ScanPhase
    /** canAskAgain 决定按钮文案是「再次申请」还是「去设置」——这是系统 API 给的信息，显式带上 */
    data class PermissionDenied(val canAskAgain: Boolean) : ScanPhase
    data object Scanning : ScanPhase
    data object Resolving : ScanPhase
}

sealed interface ScanError {
    /** 出路：重试 */
    data object Network : ScanError
    /** 出路：仅提示（用后端返回的中文文案原样展示，项目既有做法） */
    data class Rejected(val message: String) : ScanError
    /** 出路：重新选图 */
    data object NoCodeInImage : ScanError
}
```

对比一下收益：

- 非法组合**构造不出来**（sealed 保证 `PermissionDenied` 一定带 `canAskAgain`）
- 新增码类型/错误类型时，UI 的 `when` **编译期报错**，逼你处理——这是显式化最大的价值
- `error` 的每个分支天然对应一条出路，UI 不需要"猜"

```kotlin
// lib-base/scan/ScanTarget.kt —— 解析结果：四类互斥，且"哪一类"决定了后续完全不同的流程
sealed interface ScanTarget {
    /** 站内码：交后端 resolve 后才决定跳转 */
    data class InternalCode(val raw: String) : ScanTarget
    /** 登录票据（Phase 2） */
    data class LoginTicket(val ticket: String) : ScanTarget
    /** 外部 http(s) 链接：不自动打开，只提示 + 可复制 */
    data class ExternalUrl(val url: String) : ScanTarget
    /** 其它文本：展示 + 可复制。**注意它不是"错误"**——用户可能就想扫个纯文本码 */
    data class PlainText(val text: String) : ScanTarget
}
```

### 5.4 DTO 与 domain 的分界（不泄露实现）

```kotlin
// data/remote/dto/ScanResolveDto.kt —— 服务端响应形状，★ 只活在 data 层
data class ScanResolveDto(
    val type: String?,        // 服务端可能给 null，故可空
    val targetId: Long?,
    val title: String?,
    val subtitle: String?,
    val cover: String?,
)

// domain 侧的模型：字段不可空（映射时把关），且不叫 Dto
data class ScannedContent(
    val kind: ContentKind,    // enum：VIDEO / USER
    val targetId: Long,
    val title: String,
    val subtitle: String?,
    val cover: String?,
)
```

三条规矩：

1. **DTO 不出 `data` 包**。ViewModel 拿到的必须是 `ScannedContent`，不是 `ScanResolveDto`
2. **可空性在映射时收口**：服务端字段可空是因为它可能缺；映射时把"缺了就不能用"的字段校验掉（`targetId ?: return failure`），domain 模型里就是非空——**让不确定停在边界上**
3. **`type: String` → `enum ContentKind`**：字符串在边界处转换一次，之后全用枚举，避免"到处都是魔法字符串"

## 六、接口契约

### 6.1 码的内容格式

**站内码**（Phase 1）

```
https://bluebook.invalid/v/{aid}     视频
https://bluebook.invalid/u/{id}      用户
```

- host 取 `ScanCodeFormat.CODE_HOST`，**与部署地址 `BASE_URL` 解耦**（理由见 4.1）
- 路径段固定小写；末尾斜杠容忍；多余 query 忽略
- **解析只认 `ACCEPTED_HOSTS` 白名单**——不接受子域、不接受相似域名（`bluebook.invalid.evil.com` 必须判为非站内码）
- 本期用 `.invalid`（RFC 2606 保证不解析）：不会被抢注、也不会让人误以为能打开；有真域名后**追加**白名单，老码继续有效
- **必须与 R7 分享产出的链接完全一致**——由 `ScanCodeFormat` 单一定义保证

**登录码**（Phase 2，暂缓）：`https://<码域名>/qr/{ticket}`，一次性短时效，客户端不解析票据内容、不缓存、不打日志。

### 6.2 后端 HTTP 接口

沿用既有约定：`ApiResponse<T>` 信封（`code == 0` 成功）、中文 `message`、`Authorization: Bearer`。

```
GET /api/v2/scan/resolve?payload=<urlencoded 原始字符串>
```

**`payload` 传扫码得到的原始字符串，不是我方解析后的 id。**
理由：让服务端成为"算不算站内码"的**唯一裁判**。若客户端解析完只传 id，等于把判据放在客户端——
一旦后端格式变更而客户端版本落后，就会出现"新码老版本 App 扫不出来"（而老版本是改不动的）。

`data`：`type`(`VIDEO`/`USER`)、`targetId`、`title`、`subtitle`、`cover`

失败：400 这不是小蓝书的二维码 / 404 内容不存在或已删除 / 403 你没有权限查看 / 410 二维码已失效

### 6.3 客户端内部契约

- `ScanCodeFormat.parse(payload): ScanTarget` —— **不做网络、不判可见性**，只回答"这是哪一类"
- `ExtraKeys` 新增 `EXTRA_SCAN_TAG`（供与 `IMAGE_PICKER` 复用时回传）

> 顺带修一处既有毛病：`MineFragment` 跳 `IMAGE_PICKER` 时硬编码字面量 `"tag"`
> （`withString("tag", tag)`），而 `ImagePickerActivity` 定义的是 `EXTRA_TAG = "tag"`，
> 两处靠"字面量恰好相同"维系，而 `ExtraKeys` 里偏偏没有它。

**路由**：新增 `/scan/entry` → `ScanActivity`。`routeMap.json` **是手工维护的输入**（项目注释已说明），必须同步改。

## 七、功能说明

### 7.1 状态机

```
   进入 → CheckingPermission
            ├─ 授予 → Scanning ──解出字符串──→ Resolving
            │            ↑                        ├─ 成功 → 跳转 → finish()
            │            └──── 继续扫 ←──── 失败 ──┘─ 失败 → 记 error（停在本页 + 出路）
            └─ 拒绝 → PermissionDenied（页内说明 + 去设置/再次申请 + 从相册选图）
```

`Resolving` 期间 `analyzing = false`，避免同一帧连续触发。

### 7.2 失败矩阵（一个都不能静默）

| 场景 | 表现 | 对应字段 |
|---|---|---|
| 相机权限被拒 | 「去设置」或「再次申请」（看 `canAskAgain`）+「从相册选图」 | `PermissionDenied(canAskAgain)` |
| 设备无相机 | 同款降级态，文案区分 | `PermissionDenied` |
| 画面有码但识别不出 | 继续扫，不报错；无码时给「对准二维码」引导 | — |
| 格式不认识 | 按 R4 展示 + 复制；**不报错** | `ScanTarget.PlainText` |
| 校验网络失败 | 「网络连接失败，请重试」+ 重试；**保留已扫到的内容** | `ScanError.Network` + `pendingPayload` |
| 码失效/已删/无权 | 用后端中文 message 原样提示 | `ScanError.Rejected(message)` |
| 同一码连续触发 | 2 秒内去重 | — |
| 跳转目标页自己再失败 | 由目标页显示，不重复提示 | — |
| 切后台/来电 | `onPause` 释放相机，`onResume` 重建 | `analyzing` |
| 相册选图取消 | 静默回扫码态 | — |
| 相册图里没有码 | 「这张图里没有识别到二维码」 | `ScanError.NoCodeInImage` |

**注意最后几行的"出路"不同，这正是把 `ScanError` 做成 sealed 的原因**——如果只是一个 `errorMessage`，UI 只能猜该给"重试"还是"去设置"。

### 7.3 跳转规则

**默认直接跳**（扫码的直觉是"扫完就去"），但**先 resolve 成功再跳**：

- 成功 → 跳目标页并 `finish()`：视频走既有的 `openVideoPlayer(...)`（五个 extra 统一在一处拼，
  **调用点不要各自拼**）；用户走 `RoutePath.USER_PROFILE` + `ExtraKeys.EXTRA_USER_ID`
- 失败 → 停在扫码页显示原因（R5）
- `finish()` 掉扫码页，返回直接回「我的」页，**不留下一个已经扫过的扫码页**

### 8.2 关于 Phase 2 的一个建议：网页端不必是独立前端项目

"扫码登录要有网页端"这件事，最轻的做法**不是**新建一个前端工程，而是**后端直接返回一个静态页**：

```
GET /qr    → 返回一个极简 HTML（一个 <img> 显示二维码 + 一段 JS 每 2 秒轮询 /auth/qr/poll）
```

这样一个 HTML 文件 + 3 个接口就够了，不需要独立前端项目、不需要构建链、不需要部署第二个服务。
如果你接受这个做法，**Phase 2 其实不被阻塞**，只是加一个静态页的工作量。

若你不想碰任何网页，那就维持"暂缓"，Phase 1 先上——Phase 2 的接口设计（4.2 那三个）保留在文档里作为契约草案，将来直接用。

### 8.3 需要同步更正 CLAUDE.md（P3 的直接后果）

CLAUDE.md 的「权限归属」一节写的是三权全归 `:app`，与实现不符。实际情况：

| 权限 | 实际所属模块 |
|---|---|
| `INTERNET` | `:app` |
| `ACCESS_NETWORK_STATE` | `:core-network` |
| `ACCESS_COARSE_LOCATION` | `:feature-home`、`:feature-video` |
| `READ_MEDIA_IMAGES`、`READ_MEDIA_VISUAL_USER_SELECTED`、`READ_EXTERNAL_STORAGE` | `:feature-image` |
| `CAMERA`（待加） | `:feature-scan` |

**确立的规则**：**权限随使用它的模块走**——模块自洽（单独构建时声明齐全），移除模块时权限随之消失。

代价要如实写清：**审计全部权限需要翻所有模块的清单**。给一条命令即可：

```bash
grep -rh "uses-permission" --include=AndroidManifest.xml . | grep -v build | sort -u
```

### 8.4 落地步骤

见 4.5。**建议从第 1、2 步开始**：都零风险（不碰相机、后端、权限），做完能真机点进页面，
也能看到 `ScanCodeFormat` 的单测全绿——**先把"什么算合法码"这个安全边界钉死**，再接相机。

### 8.5 包体实测（第 3 步接完后的真实数字）

第 3 步把 CameraX + ML Kit 接进来后，**debug APK 从 48.9 MB 涨到 68.1 MB（+19.2 MB）**。
拆开看，增量几乎全是 native 库：

| 项 | arm64-v8a | 4 个 ABI 合计 |
|---|---|---|
| `libbarhopper_v3.so`（ML Kit 条码引擎） | 4.16 MB | ~16.6 MB |
| `libimage_processing_util_jni.so`（CameraX） | 0.03 MB | ~0.1 MB |
| **合计** | **4.18 MB** | **17.46 MB** |

两条结论：

1. **单 ABI 的真实成本是 ~4.2 MB**（真机只需要它）。第 4 节讨论选型时我口头估的是"2~3MB"，
   偏低了约 40%。
2. **APK 多出的 ~13 MB 纯粹是"打了 4 个 ABI"**。debug 包默认不分 ABI，而手机是 arm64。
   想省这 13 MB 有两个办法，各有代价：
   - `ndk { abiFilters += "arm64-v8a" }`：最小改动，但**x86/x86_64 模拟器装不上**（将来想用模拟器
     测就得改回来）
   - ABI splits / App Bundle：每个 ABI 出一个包，但要选对包分发

**这条也修正了对 ZXing 的取舍判断**：`zxing-android-embedded` 是**纯 Java、无 native**，
所以真实差距是 **+17.5 MB（或加 abiFilters 后 +4.2 MB）对 +~1 MB**——而不是笼统的"包体大小不同"。
本项目目前给约 10 人直接分发 debug APK、不开 ABI 拆分，所以这个差值是实打实的。
`BarcodeScanner` 已接口化，真要换只改 `MlKitBarcodeScanner` 一个文件（见第 3 步的提交）。
