## 本清单的取舍说明

审计报告共 69 项发现，其定级基于「公网暴露 + 匿名攻击者」的威胁模型。按当前的实际场景，**安全类发现（JWT 默认密钥、验证码明文返回、上传 IDOR、明文 HTTP、日志泄露等）全部移出本清单**，保留在审计报告中作为对外提供服务前的检查表——它们的问题不是「不真实」，而是触发前提（存在能访问到你 API 的攻击者）在当前不成立。

本清单只收**与攻击面、用户量、是否上线无关**的项：功能本身就是坏的，或者虚拟机部署这一形态会放大触发概率的项。

| 序号 | 问题 | 影响 | 改动范围 |
|---|---|---|---|
| 1 | 收藏他人视频必定 500（P2-B2） | 功能已坏 | 后端 + 1 条 DDL |
| 2 | 评论以 `user_id = 0` 落库，显示成无作者（P0-3 的功能面） | 用户可见 | 后端 + 客户端不用改 |
| 3 | 首页加载失败白屏，无提示无重试（P2-F3） | 虚拟机时开时关 → 高频 | 客户端（2 个页面） |
| 4 | 来源模式在缺参数时被丢弃（原 P1-10，**已降级为边缘缺陷**） | 参数异常时静默串源 | 客户端（3 个文件） |
| 5 | 无备份 + 转码卡死不自愈（可用性） | 数据丢失 / 视频消失 | 后端 + 部署 |
| 6 | 评论点赞计数被永久改坏，可显示负数（P1-9） | 用户可见 | 客户端（1 个文件） |

建议执行顺序：**1 → 2 → 5 →（3、4、6 合一次发版）**。前三项只动后端，重启服务即可；最后一步需要重新出包给现有用户。

第 4 项经核实后**不是用户日常会撞到的 bug**（原判断有误，更正过程见该节），保留在清单里的理由是修复成本低、且能避免将来参数改动后出现难以定位的「点开我的喜欢看到随机视频」。若时间紧，可以只做第 1、2、3、5、6 项。

> **本清单的边界**：只收「与攻击面、用户数、是否上线都无关」的问题——即功能本身就是坏的。另有几项**今天确实存在、但触发频率较低**的用户可见问题（播放器偶发黑屏、图片解码 OOM、上传断点无续传），它们的性质与上线门槛无关，只是因为不常撞到而被排到后面，单独列在文末「[频率较低但今天仍存在](#频率较低但今天仍存在的问题)」一节——**不要**把它们理解为「上线前才需要处理」。

## 改动 1：收藏他人视频返回 500

### 先验证（1 分钟）

```sql
-- 1) 确认 ENUM 里确实没有 COLLECT
SELECT COLUMN_TYPE FROM information_schema.COLUMNS
WHERE TABLE_SCHEMA = 'blue_book' AND TABLE_NAME = 'notification' AND COLUMN_NAME = 'type';

-- 2) 确认严格模式（有 STRICT_TRANS_TABLES 就会写入失败）
SELECT @@sql_mode;

-- 3) 看表规模，决定 DDL 风险
SELECT COUNT(*) FROM notification;
```

或者更直接：用 A 账号收藏 B 账号的视频一次，看是否报错。自己收藏自己不会触发（`VideoService.kt:127` 有 `userId != video.uploaderId` 判断），所以这条 bug 只在收藏**别人**的视频时出现。

### 根因

`backend/src/main/resources/schema.sql:98` 定义 `type ENUM('LIKE','COMMENT','FOLLOW','SYSTEM')`，而 `notification/entity/Notification.kt:40` 的 `NotifyType` 有 `COLLECT`，且 `VideoService.collectVideo` 会写入它。MySQL 8 默认严格模式下写不存在的 ENUM 值会报 "Data truncated for column 'type'"，整个 `@Transactional collectVideo` 回滚。

### 改动

**文件 1**：`backend/src/main/resources/schema.sql:98`

```diff
-    type ENUM('LIKE','COMMENT','FOLLOW','SYSTEM'),
+    -- 注意：新增值必须追加在末尾。ENUM 的顺序决定内部序号，
+    -- 插在中间会触发整表重建（ALGORITHM=COPY）来重排序号。
+    type ENUM('LIKE','COMMENT','FOLLOW','SYSTEM','COLLECT'),
```

**文件 2**：在线库执行同样的变更

```sql
ALTER TABLE notification
  MODIFY type ENUM('LIKE','COMMENT','FOLLOW','SYSTEM','COLLECT');
```

`COLLECT` **必须追加在末尾**。若插在 `FOLLOW` 之前，MySQL 需要重排已有行的内部序号并重建整表；追加在末尾才是 in-place 的。

### 验证

1. **重启应用必须成功**。这一步同时验证了审计报告中「待确认项 1」——Hibernate 6 的 `ddl-auto: validate` 是否能接受 MySQL 的 ENUM 列。若启动失败，说明 validate 不接受 ENUM，此时再决定是把这些列改成 `VARCHAR(20)` 还是调整 validate 策略（那是一次更大的改动，先回来讨论）。
2. A 账号收藏 B 账号的视频 → 返回成功，且 `SELECT * FROM notification ORDER BY id DESC LIMIT 1` 能看到 `type = 'COLLECT'`。
3. 自己收藏自己的视频仍正常，且不产生通知。

### 回滚

DDL 可逆（`MODIFY` 回原列表），但需先删除 `type = 'COLLECT'` 的行。**执行前先备份**（见改动 5a）。

**风险**：低。10 个用户的表大概率只有几百行。但这是本清单中**唯一改动生产库结构**的操作，务必先做备份。

## 改动 2：评论以 `user_id = 0` 落库

### 根因（这条链条要看清楚，因为它是「安全发现的功能面」）

1. `CommentBottomSheet.kt:167` 判断的是**内存里的 `currentUser.userId`**，不是 token 是否有效。
2. access token 的有效期是 1 天（`application.yml` 的 `access-token-ttl: 86400000`），而过期**不会**清空 `CurrentUser`——只有刷新失败才会（`TokenAuthenticator.kt:63-66` 的 `onSessionExpired`）。
3. 于是存在一个窗口：`CurrentUser` 说「已登录」，但 token 已过期。
4. 此时点发送，请求发出去，而 `POST /api/v1/comments` 同时在 `SecurityConfig.kt:28` 的 `permitAll` 和 `JwtAuthFilter.PUBLIC_PATHS` 里（`:23`），后端**既不校验也不返回 401**，所以不会触发 token 刷新。
5. `CommentController.currentUserId()`（`:15-16`）拿不到 principal 就返回 `0`，评论以 `userId = 0` 落库。
6. `CommentService.toDto`（`:117`）执行 `userRepository.findById(0)` → null → `nickname` 和 `avatar` 都是空串 → **评论显示成没有作者**。
7. 同时 `incrementCommentCount` 已经加过 1，所以评论数和列表长度是对得上的，表面上一切正常。

结论：这不是「有人恶意调用接口」，而是**你自己用户正常操作就能撞上**的状态。

### 为什么客户端不用改

后端返回 401 后，客户端既有链路会自行做对的事：

- token 过期但存在 → `TokenInterceptor` 照常附加 → 服务端 401 → `TokenAuthenticator` 用 refresh token 换新 token 并重放 → **用户无感成功**。
- refresh 也失败 → `clearSession()` + `CurrentUser.clear()` → 下次点击时 `CommentBottomSheet.kt:167` 的 `currentUser.userId == null` 成立 → 弹出登录引导。

这比在客户端加「token 是否有效」的判断更可靠，因为 token 有效性只有服务端说了算。

## 改动 4（已更正）：来源模式在缺参数时被丢弃

> ⚠️ **更正说明**：本节此前把问题描述为「空态点『重新加载』会跳到随机流」，**该结论不成立**，是我上一轮基于子审计结论未加核实就采纳的错误。核实后的实际情况与修法见下。请以本节为准，审计报告中 P1-10 的描述与定级也需要按本节修正（它应降级为「边缘缺陷」而非用户可感的 bug）。

### 为什么原判断不成立

原判断假设「我的喜欢」页面会出现空态。实际链路是：

4. 空态的显示条件是 `state.items.isEmpty()`（`VideoFragment.kt:237`）——**Liked/Collected/UserVideos 三种模式下 `items` 至少有首条，空态永不出现**。

### 5b 卡在 `PROCESSING` 的视频永远不出现

**根因**：`TranscodeConsumer.doTranscode`（`:37-39`）先把状态置 `PROCESSING` 并保存，之后如果进程重启、被杀或异常退出，这一行就永久停在 `PROCESSING`。而 feed 查询要求 `transcodeStatus = 'DONE'`（`VideoRepository.kt:15`），所以视频**永远不会出现在任何人的信息流里**。

`ScheduledTasks` 里没有任何兜底——`cleanExpiredUploads`（`:54-58`）和 `dailyReconciliation`（`:41-49`）都是只有注释的空壳。

注意 `remove` 必须放在 `launch` 块的末尾、而不是 `.onFailure` 里——成功路径同样要解锁，否则一次成功后该评论再也点不动。放在 `launch` 内而不是用 `.also`，是因为 `likeCommentUseCase` 若抛异常（而非返回失败的 `Result`）时 `launch` 会被取消，此时 `togglingLikeIds` 会残留；若想更稳妥可以用 `try/finally`。

**改动 4**：`updateCommentLike`（`:292-306`）加下限保护

```diff
 				comment.id == commentId -> comment.copy(
 					isLiked = isLiked,
-					likeCount = if (isLiked) comment.likeCount + 1 else comment.likeCount - 1
+					likeCount = if (isLiked) comment.likeCount + 1
+								else (comment.likeCount - 1).coerceAtLeast(0)
 				)
```

`updateCommentLike` 是**递归处理 `replies` 的**，改动要覆盖嵌套分支——上面的三处改动都作用于同一个函数/同一层查找，递归逻辑不变。

### 验证

- **双击**：快速连点同一评论的心形 5～6 次 → 计数只能变 1（因为第二次起被忽略），界面与服务端一致。
- **失败回滚**：断网状态下点赞 → 计数应回到原值，`isLiked` 回到原状态，**多次重复后计数不漂移**（这是原来的 bug，要专门反复试）。
- **零值下限**：找一条 `likeCount = 0` 的评论，断网点赞 → 不能出现 `-1`。
- **成功路径解锁**：点赞成功后（联网）再次点击应仍然有效（回归验证 `remove` 的位置正确）。
- **回复层级**：对某条**回复**点赞，行为与根评论一致（验证 `findIn` 的递归）。
- **与改动 2 的交互**：改动 2 上线后游客点赞会被服务端拒（401），此时应只见错误提示、计数不动。

### 风险

低，纯客户端。唯一需要注意的是 `togglingLikeIds` 若因异常残留会让该条评论"点不动"——上面提到的 `try/finally` 是更稳的写法，建议直接用：

```kotlin
viewModelScope.launch {
    try {
        likeCommentUseCase(commentId, newLiked).onFailure { e -> /* 同上 */ }
    } finally {
        togglingLikeIds.remove(commentId)
    }
}
```
