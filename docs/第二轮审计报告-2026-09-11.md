**最该先看的三条**

1. **裁剪页从来不显示图片**（首轮遗漏，已亲自核实）。`CropImageView.onDraw()` 只画遮罩、九宫格与裁剪框，`super.onDraw()` 画的是 ImageView 的 drawable——**而这个 drawable 从未被设置过**。全项目没有任何 `setImageBitmap`/`drawBitmap` 调用，布局里也没有 `android:src`。用户面对的是黑底 + 白色裁剪框，**在看不见照片的情况下裁剪**。默认矩阵把图片居中，所以直接点「完成」得到的是居中裁剪，看起来是对的——这大概是它一直没被发现的原因。**修复只需一行**（见后）。
2. **上传重试会重复发布同一条视频**（本轮引入，`PublishViewModel.kt:109-134`）。重试循环把**非幂等的 `publish` POST 也包了进去**：响应丢失时重试会再走一遍 init→complete→**publish**，而后端 `publish` 无条件 `insert`，于是同一条视频出现两条记录、两个转码任务，且没有任何地方会对账消除。
3. **过期转码兜底可能让两个 ffmpeg 同时写同一个输出目录**（本轮引入，`ScheduledTasks.kt:88-101`）。兜底查询包含 `PROCESSING`，阈值 30 分钟；而 `transcode-worker.sh` 用 `-y` 写同一组 `1080p_%03d.ts`/`m3u8`。一个超过 30 分钟的正常转码（1080p 在 2 vCPU 虚拟机上现实存在）会被重复投递，两个进程交错写切片，**谁先退出 0 谁把它标成 DONE**，产出损坏的 HLS 且无法从数据库看出来。我原先写的「重复投递的代价只是多跑一次 ffmpeg」是错的——代价是并发写。

## 一、本轮改动引入的问题（13 项）

### R1　[High] 上传重试把非幂等的 `publish` 也纳入重试，响应丢失即重复发布
**位置**：`feature-video/.../ui/publish/PublishViewModel.kt:109-134`
```kotlin
for (attempt in 0 until MAX_RESUME) {          // 3 次
    try {
        val init = publishRemote.initUpload(initRequest).getOrThrow()
        ...
        uploadChunks(init.uploadId, fileName, totalChunks, uploaded)
        val filePath = publishRemote.completeUpload(init.uploadId).getOrThrow()
        publishRemote.publish(PublishRequestDto(...)).getOrThrow()   // ← 非幂等
        return@runCatching Unit
    } catch (t: Throwable) { ... }
}
```
**影响**：`publish` 每调一次就插一行（`VideoService.kt:84-95` 无去重、无幂等键）。移动网络丢响应、读超时、进程冻结都会触发重试，而重试会**再发布一次**——同一条视频出现两条，永久存在。次要影响：`11003 视频正在转码中` 这类不可重试的业务失败也会被重试 3 次（1s/2s 退避）才给用户提示。
**修复**：只重试到 `completeUpload` 为止；`publish` 不重试，或加客户端生成的幂等键 + 服务端唯一校验。

### R2　[High] 转码兜底可能并发跑两个 ffmpeg，写出损坏的 HLS
**位置**：`backend/.../common/ScheduledTasks.kt:88-101`、`video/repository/VideoRepository.kt:20-21`、`video/service/TranscodeConsumer.kt:18-33`、`resources/transcode-worker.sh`
**影响**：见摘要第 3 条。`TranscodeConsumer` 无状态互斥（不检查是否已在处理），worker 脚本 `-y` 覆盖写同一目录，且运行中的 ffmpeg 不会随 JVM 退出而终止。兜底还会刷新 `updated_at`，使该模式每 30 分钟可重复一次。
**修复**：兜底只捞 `PENDING`（或引入心跳列判断 worker 是否真的死了）；consumer 发现行已是 `PROCESSING` 时跳过；worker 先写临时目录再原子改名；per-video 加锁（文件锁或 Redis `SETNX`）。

### R3　[Medium] 兜底用 detached 实体整行 merge，会回退 `DONE`/`hlsUrl` 与期间累计的计数
**位置**：`backend/.../common/ScheduledTasks.kt:96-101`
**影响**：`findStaleTranscodes` 在自己的只读事务里读出实体（脱离上下文），`save(video)` 走 `em.merge`；`Video` 没有 `@DynamicUpdate`，于是 UPDATE 覆盖**所有列**，值来自读取时的快照。两种具体交错：(a) 一条重复消息正在处理并已写 `DONE` + `hlsUrl`，merge 把它改回 `PENDING` + `hlsUrl=null`，视频从 feed 再次消失；(b) 期间累计的 `view_count`/`like_count`/`comment_count` 被静默回退——`PENDING` 视频是可被观看与点赞的（`findUserVideosCursor` 不过滤转码状态）。
**修复**：改为定向批量更新，并让状态复查与写入原子化：
```kotlin
@Modifying
@Query("UPDATE Video v SET v.transcodeStatus = 'PENDING', v.updatedAt = CURRENT_TIMESTAMP WHERE v.id = :id AND v.transcodeStatus IN ('PENDING','PROCESSING')")
fun markStaleTranscodePending(id: Long): Int
```

### R4　[Medium] 每日对账是五条全表 UPDATE 挤在一个事务里，且缺少支撑索引
**位置**：`backend/.../common/ScheduledTasks.kt:65-78`、`video/repository/VideoRepository.kt:27-46`、`resources/schema.sql:66-78`
**影响**：`UPDATE video v SET v.like_count = (SELECT COUNT(*) ...)` 没有 `WHERE`，InnoDB 对整个 `video` 表加 X 锁直到事务结束；而 `video_like`/`video_collect` 的主键是 `(user_id, video_id)`，`video_id` 不是前导列，每条子查询都是扫描。凌晨 3 点任何并发的 `reportView`/点赞/发布都会阻塞在这些行上，超过 `innodb_lock_wait_timeout`（默认 50s）后以 500 `14999` 失败。失败会整体回滚（正确性没问题，问题是阻塞与随数据量增长的成本）。
**修复**：拆成五条独立事务；给 `video_like`/`video_collect` 加 `INDEX idx_video_id (video_id)`；只更新确实漂移的行。

### R5　[Medium] `cleanExpiredUploads` 以「创建时间」计过期：会删掉仍在活跃的会话，也让新的续传功能在 24 小时后失效
**位置**：`backend/.../common/ScheduledTasks.kt:110-121`、`file/service/ChunkUploadService.kt:64-78`、`file/entity/UploadSession.kt:38-39`
**影响**：`upload_session.updated_at` 只在插入与 `completeUpload` 时写；`uploadChunk` 写分片文件和 Redis 却**不碰这一列**，`initUpload` 的续传分支也不碰。所以这一列实际含义是「会话创建时间」而非「最后活动时间」。两个后果：(a) 一个还在持续收分片的会话会被删除，下一次 `uploadChunk` 得到 `13002 上传会话不存在或已过期`；(b) 用户中断一天后重传时拿到全新 `uploadId`、`uploadedChunks` 为空，**本轮新加的客户端续传静默退化为全量重传**。
**修复**：在 `uploadChunk`（以及 `initUpload` 的续传分支）里 `session.updatedAt = LocalDateTime.now(); save(session)`，让过期语义变成「24 小时无活动」。

### R6　[Medium] 池满时 `preload` 自我抖动：新引擎建好就立刻把上一页的预加载淘汰掉
**位置**：`core-player/.../PlayerEnginePool.kt:45`、`:50`、`:74`；调用方 `feature-video/.../VideoFragment.kt:110-111`
**影响**：`preloaded` 是插入序 LinkedHashMap，`trim()` 淘汰 `keys.first()`（最旧）。当 `owned == maxSize` 且 `idle` 为空时，`preload(position+2)` 会**先构造一个全新 ExoPlayer（并开始网络请求）**，然后 `trim()` 立刻释放掉更早的 `preload(position+1)`。于是每次翻页都构造一个、销毁一个，**相邻页的预加载永远不存在**，`bind()` 时要在关键路径上重新构造并起播。功能没坏，但预加载窗口实际塌缩为一页且持续抖动——这与引入预加载的目的相反。
**修复**：`trim()` 不淘汰刚插入的条目（例如淘汰「距离当前播放位置最远」的预加载，或在容量不足时直接跳过本次 preload）。

### R7　[Medium] `home_focus_error` 对游客可能卡在可见，叠在未登录空态上
**位置**：`feature-home/.../HomeFocusFragment.kt:159-162`（只在状态收集器里算可见性）对比 `:72-73`（`isGuest` 在 IO 跳转后才赋值）
**影响**：`repeatOnLifecycle` 重启时收集器会先重发一次当前状态，而 `onResume` 里的 IO 登录态检查此时尚未完成，`isGuest` 还是上一轮的值。已登录用户遇到加载失败（state 保留 `message`）→ 登出 → 回到该 Tab：`failed` 用陈旧的 `isGuest=false` 计算 → 错误浮层显示；之后 `isGuest=true` 不会重新计算可见性（只在状态变化时算），于是游客同时看到「登录后查看关注内容」和「加载失败／重新加载」，且重试按钮会为游客发一个必然 403 的请求。
**修复**：把可见性计算抽成 `renderError()`，在收集器与 `isGuest` 赋值后都调用（或用 state + isGuest 的 combine 驱动）。

### R8　[Medium] 裁剪保存期间视图被销毁，结果被静默丢弃
**位置**：`feature-image/.../ImageCropFragment.kt:122-137`
**影响**：`viewLifecycleOwner.lifecycleScope` 在 `onDestroyView` 被取消，`withContext(Dispatchers.IO)` 恢复时抛 `CancellationException`，于是 IO 之后的代码一句都不执行：JPEG 已经写进 `cacheDir`，但 `finishWithResult` 永不触发，选择器返回空，按钮保持禁用。用户旋转屏幕或中途离开，裁剪结果无声丢失。
**修复**：写文件与 `finishWithResult` 放到比视图更长的作用域（Activity 的 `lifecycleScope` 或 ViewModel 作用域）。

### R9　[Medium] 对账日志打的是「匹配行数」而非「改动行数」，我给出的验证步骤永远不可能通过
**位置**：`video/repository/VideoRepository.kt:27-46`、`auth/repository/UserRepository.kt:24-37`（注释写「返回实际改动的行数」）、`ScheduledTasks.kt:74-77`（日志「点赞校正 {} 行」）
**影响**：JDBC URL（`application.yml:9`）未设 `useAffectedRows`，Connector/J 默认 `useAffectedRows=false` 会带 `CLIENT_FOUND_ROWS`，MySQL 返回**匹配**行数。由于没有 `WHERE`，每次调用都返回 `video`/`user` 的全表行数。而我在清单里写的验证方式是「看日志的『点赞校正 1 行』」——**它会打印全表行数**，验证者会以为任务坏了，或者对真正的异常视而不见。这条同时是我自己文档的错误，值得一并修。
**修复**：显式统计漂移行数（对 `like_count <> (SELECT COUNT(*) …)` 计数后/前对比），或把注释与验证步骤改成「匹配行数」。

### R10　[Low] 续传时进度会回退
**位置**：`feature-video/.../ui/publish/PublishViewModel.kt:116-118` 对比 `:187`
**影响**：若 `uploadedChunks` 不是前缀（如 `{0..49, 60..99}`），预填显示 90%，而第一个待传分片（index 50）算出 51%——进度条往回跳，观感上像丢数据。
**修复**：`progress = maxOf(state.progress, computed)`。

### R11　[Low] `CancellationException` 的重抛被外层 `runCatching` 吞掉，这道防线实际无效
**位置**：`feature-video/.../ui/publish/PublishViewModel.kt:97`（`runCatching {`）、`:137`（`if (t is CancellationException) throw t`）
**影响**：`runCatching` 捕获 `Throwable`，所以重抛会被转成 `Result.failure(CancellationException)` 并照旧走到 `runResult` 的 `onFailure`——正是这行想避免的行为（用户离开页面被报成「发布失败」）。实际影响小（effect 收集器通常已经没了），但这行防线等于没写。
**修复**：重试循环用显式 `try/catch` 而不用 `runCatching`，在构造 Result 之前重抛取消。

### R12　[Low] `maxSize` 只是建议值：全部被持有时会超出
**位置**：`core-player/.../PlayerEnginePool.kt:70-77`（`else -> return`）
**影响**：`maxSize = 5`，而 ViewPager2 可能同时持有 5 个 holder（`offscreenPageLimit` 内的 3 个 + 视图缓存里最多 2 个已 detach 但未 recycle 的），此时下一次 `preload` 会让存活实例超过 5——每个 ExoPlayer 各占缓冲与解码器。这是我在类注释里写明的刻意取舍，但相对「硬上限 5」确实是内存规划上的退步，需要在低内存设备上实测。
**修复**：若要硬上限，在 `owned.size >= maxSize` 时直接跳过 preload（而不是先建再淘汰）。

### R13　[Low] `JwtAuthFilter` 的新注释引用了已删除的方法
**位置**：`backend/.../config/JwtAuthFilter.kt:20-22` 写「否则 `currentUserId()` 会得到 0」，而 `currentUserId()` 已在同一次提交里从 `CommentController` 删除。纯维护隐患。

## 二、首轮遗漏（12 项）

### F1　[High] 裁剪页从来不绘制图片
**位置**：`feature-image/.../ui/image/CropImageView.kt:107-130`（`onDraw`）、`:80-92`（`setBitmap`）；布局 `feature-image/src/main/res/layout/fragment_image_crop.xml`
**证据**（已亲自核实）：`onDraw` 只做 `super.onDraw(canvas)` + 遮罩 + 九宫格 + 裁剪框；`bitmap` 只被赋给私有字段，从未交给 ImageView。全项目 `grep -rn "setImageBitmap\|drawBitmap"` → 无命中；大小写不敏感搜框架版 `setImageURI` → 只命中我自己在 `feature-mine` 的两条注释；布局中 `CropImageView` 无 `android:src`，也没有承载图片的兄弟 ImageView；`git log -S "drawBitmap"` 显示该文件从未有过。
**影响**：裁剪页显示为黑底 + 白色裁剪框 + 九宫格，看不到照片。拖拽/缩放仍在操作（改的是 `drawMatrix`），`getCroppedBitmap()` 也照此矩阵裁切——**用户在盲操**。初始矩阵把图片居中，所以不拖动直接点「完成」得到居中裁剪，结果看起来正常；这解释了它为何未被发现。任何想重新取景的用户都会看到全黑，多半会以为图片加载失败。
**修复**：在 `setBitmap` 里把位图交给 ImageView 自己绘制（顺序上先设置 drawable 再回收旧图，避免中间态）：
```kotlin
fun setBitmap(newBitmap: Bitmap?) {
    val old = bitmap
    bitmap = newBitmap
    // 本类 onDraw 只画遮罩/九宫格/裁剪框，图片由 ImageView 绘制：
    // super.onDraw 画的是 ImageView 的 drawable，此前从未设置过 → 裁剪页看不到图片
    setImageBitmap(newBitmap)
    if (old != null && old !== newBitmap && !old.isRecycled) old.recycle()
    if (newBitmap != null && width > 0) { updateCropRect(); applyInitialMatrix() }
    invalidate()
}
```

### F2　[High] 评论/通知时间戳按 UTC 解释本地时间，界面永远显示「刚刚」
**位置**：`backend/.../comment/service/CommentService.kt:138`、`backend/.../notification/service/NotificationService.kt:37`
```kotlin
createTime = comment.createdAt.toEpochSecond(ZoneOffset.UTC) * 1000
```
**影响**：`createdAt` 来自 `LocalDateTime.now()`（`common/BaseEntity.kt:23,27`），是**宿主机本地墙钟时间**；把它当成 UTC 换算成 epoch，非 UTC 的 JVM 上会**偏到未来**（+08 即 +8 小时）。客户端用 `System.currentTimeMillis() - timestamp` 算相对时间（`CommentAdapter.kt:150-160`、`ReplyAdapter.kt:68`、`MessageAdapter.kt:83-93`），`diff` 为负 → 命中第一个分支 → **所有评论与通知恒显示「刚刚」**，「N分钟前/小时前/天前」永远不会出现。两个独立审计路径各自发现了这条。
**注**：若 JVM 跑在 UTC 则当前代码碰巧正确——但修复方向在两种情况下都正确，所以无论环境如何都该改。
**修复**：`createdAt.atZone(ZoneId.systemDefault()).toInstant().toEpochMilli()`（两处），更彻底的做法是端到端用 UTC/`Instant` 并在客户端格式化。

### F3　[Medium] `deleteComment` 无条件递减 `comment_count`，重复 DELETE 即破坏计数
**位置**：`backend/.../comment/service/CommentService.kt:91-99`
**影响**：`findById` 不检查 `status`，作者（或客户端的 `RetryInterceptor` 重试、丢失响应的重发）可对同一条评论 DELETE N 次，视频 `comment_count` 每次减 1，而评论只删了一条——计数会降到 0 以下，且对所有观众可见（`Video2Dto.commentCount`）。对照 `likeComment` 用了 `if (deleted > 0)` 守卫，这里漏了。每夜对账最多 24 小时后才修好。
**修复**：用 `findByIdAndStatus(commentId, NORMAL)`，或计数递减加 `AND comment_count > 0` 条件。

### F4　[Medium] 转码完成后整行 merge，回退转码期间累计的计数
**位置**：`backend/.../video/service/TranscodeConsumer.kt:22-28`（读）与 `:63-76`（写）
**影响**：实体在 ffmpeg 开始前读出，结束时 `save(video)`——`Video` 无 `@DynamicUpdate`，UPDATE 覆盖所有列，值来自转码前快照。发布后立刻打开视频（客户端发布成功就跳转）让作者点赞/评论/上报播放，这些只要求 `status = PUBLISHED`，而 `findUserVideosCursor` 在 `PENDING`/`PROCESSING` 期间就列出该视频。于是转码一结束，这些交互的计数被抹掉，而 `video_like`/`comment` 行还在——计数与点赞状态不一致，直到凌晨 3 点对账。
**同源问题（更严重的一处）**：`user/service/UserService.kt:34-54` 的 `ensureXhsId` 也会 `userRepository.save(user)`，而它被 **`permitAll` 的 `GET /api/v2/users/{id}`** 触达（`:110-119`）——一次未认证的读会做整行 merge 写，可以回退并发的 `PUT /api/v2/me/bio`。
**修复**：consumer 改为短事务内重读+定向更新（或直接 `UPDATE video SET transcode_status=..., hls_url=..., cover_url=...`）；`ensureXhsId` 改为 `UPDATE User u SET u.xhsId = :xhsId WHERE u.id = :id AND u.xhsId IS NULL`。

### F5　[Medium] `feature-message` 的加载失败被写进 state 后从不渲染
**位置**：`feature-message/.../ui/message/MessageViewModel.kt:48`、`:71` 写 `message`；`MessageFragment.kt:166-172` 只读 `items`，而 `ShowToast` 仅由 `delete`/`clearAll` 发出
**影响**：无网下拉刷新只是停掉转圈，列表照旧、无提示、无重试；**首次加载失败时会显示「暂无消息」空态**——把请求失败说成没有消息。`loadMore` 失败则静默截断列表而 `hasMore` 仍为 `true`，继续下滑会一直无声失败。这是首轮 P2-F3 命名的同一类问题在「最一致的模块」里的新实例。
**修复**：渲染 `state.message` 并给重试入口（`AfterSearchFragment`/`AuthorProfileFragment` 已有范例），或在刷新/加载更多失败时发 toast。

### F6　[Low/Medium] 引擎按 `playUrl` 而非视频身份做 key，本条修复针对的别名问题可能重现
**位置**：`core-player/.../PlayerEnginePool.kt:24-36`；调用方 `VideoAdapter.kt:274`、`:397`、`:436`、`:164`
**影响**：池的所有权是按 key 的，不是按 holder 的。若两个列表项携带相同 `playUrl`，holder A 的 `release(url)` 会移除 holder B 仍在使用的条目（引擎转空闲→暂停→交给 C，C 的 `bindTo` 抢走 surface），B 之后的 release 又移走 C 的条目——本轮要消除的黑屏会重现。当前 feed/详情是 per-video-id 的 HLS 路径，需要出现重复 `playUrl` 才触发；但**本轮新增的续传让同一文件被重复发布变得更容易**（见 R1），而那会产生两条 `originalUrl` 相同的记录。我在 `VideoAdapter` 里写的注释读起来像是别名问题已彻底消除，这点需要更正。
**修复**：按 `aid` 或 `aid+url` 做 key。

### F7　[Low] `unfollow` 的派生删除返回「找到数」而非「删除数」，并发下可能重复递减且无下限
**位置**：`backend/.../user/service/UserService.kt:133-140`、`user/repository/UserFollowRepository.kt:11`、`auth/repository/UserRepository.kt:20-22`
**影响**：Spring Data 的派生 delete 先 `getResultList()` 再逐条 `em.remove`，返回的是**查到**的行数；实体没有 `@Version`，落败事务不会抛 `StaleStateException`。两个并发的取消关注（双击、或重试）都认为删掉了 1 行，于是发出两次 `follower_count = follower_count - 1`，计数向下漂移甚至为负。本轮把「丢失更新」方向修对了，这是反方向。
**修复**：改批量 `DELETE` 拿真实影响行数，并给递减加 `AND follower_count > 0`。

### F8　[Low] 客户端入参错误一律变成 500 `14999`
**位置**：`backend/.../common/GlobalExceptionHandler.kt:47-52`
**影响**：`GlobalExceptionHandler` 未继承 `ResponseEntityExceptionHandler`，也没有 `AuthenticationEntryPoint`，所以以下都落进兜底：缺 `videoId` → `MissingServletRequestParameterException`；`?size=abc`/`?liked=xyz` → `MethodArgumentTypeMismatchException`；请求体畸形或 Kotlin 非空字段为 null → `HttpMessageNotReadableException`；`?size=0` → `PageRequest.of` 的 `IllegalArgumentException`；`/search/suggest?limit=-1` → `List.take(-1)`；`PUT /me/birthday` 传无法解析的日期 → `DateTimeParseException`。用户看到「服务器繁忙」+ 服务端 ERROR 级堆栈，真正的故障会被噪音淹没。
**修复**：为上述异常各加 400 处理器，并给分页参数加 `require(size in 1..50)` / `coerceIn`。

### F9　[Low] `GET /api/v2/search/suggest` 不在 `permitAll`，游客的「猜你想搜」永远是静态兜底
**位置**：`backend/.../config/SecurityConfig.kt:25-39` 放开了 `/api/v2/search/hot` 却漏了 `/suggest`；客户端 `feature-home/.../SearchFragment.kt:78,110` 用 `getOrNull()`/`ifEmpty { SUGGESTED }` 把失败吞掉
**影响**：本轮为了游客看评论刚扩过 `permitAll`，但另一个游客向的读接口仍是裸 403（空 body），客户端静默回退到硬编码列表，等于该接口对所有游客无效。
**修复**：把 `/api/v2/search/suggest` 加入 `permitAll`。

### F10　[Low] 首页/关注页「已有内容时刷新失败」完全静默
**位置**：`HomeFindFragment.kt:133`（错误浮层以 `items.isEmpty()` 为条件）、`HomeFocusFragment.kt:159`；两个 VM 的 `refresh()` 失败只写 `message`、不发 toast
**影响**：下拉刷新失败只是停掉转圈，用户无法判断是刷新成功还是失败。本轮的改动只覆盖了「空列表」这一种情形。
**修复**：刷新/加载更多失败时无条件发 toast（浮层仍可以只在空列表时出现）。

### F11　[Low] `releaseEngineToPool` 提前返回跳过 `resetSpeed()`，残留「2x」角标
**位置**：`feature-video/.../VideoAdapter.kt:150-167`
**影响**：`playUrl` 为空（转码中）的条目 `engine == null`，长按仍会让提示条可见（`binding.videoItemSpeedHint`），而提前返回跳过了 `resetSpeed()`；`bind()` 也不重置该视图可见性。holder 被复用后，不相关的视频上会残留一个「2x」角标。纯视觉，且窗口很窄（未复现，标记为未证实）。

### F12　[Low] `bitmap.compress()` 的返回值被忽略
**位置**：`feature-image/.../ImageCropFragment.kt:128`
**影响**：压缩失败返回 `false` 时代码照旧返回该文件路径，上游会把一个空/截断的 JPEG 当成功上传。加一个 `if (!ok) error("保存失败")` 即可。

## 三、首轮判定「安全」区域的复核结论

三路审计对首轮结论做了独立复核，**除下列两点外维持原判**：

- **`sumInteractionsByUploader` 的 `Array<Any>` 不是 bug**：Spring Data 把数组视为集合类（`TypeDiscoverer.isCollectionLike()`），单行结果返回 `Object[]{row}`，`UserService.kt:58` 的 `.firstOrNull() as? Array<*>` 成立。首轮未明确覆盖，此处确认无问题。
- **`RetryInterceptor` 不会重试 POST**：`shouldRetry` 只允许 `GET`/`HEAD`（`RetryInterceptor.kt:41-43`），所以「重试导致重复副作用」在传输层不存在（R1 的问题在业务层）。
- **枚举与 schema 已完全对齐**：五处 `@Enumerated(EnumType.STRING)` 列均与 `schema.sql` 匹配，除已修的 `COLLECT` 外无其他不一致。
- **`MIGRATION_1_2` 正确**：`ALTER TABLE ... ADD COLUMN is_followed INTEGER NOT NULL DEFAULT 0` 与 `UserEntity.isFollowed: Boolean = false` 一致；从 git 取回 v1 实体比对，v1→v2 校验会通过。
- **裁剪数学正确**：cover 缩放、逆矩阵映射与两处 `coerceIn` 区间（下界不会超过上界，因为覆盖条件保证 `dispW ≥ cropW`）、EXIF 八种方向的映射表均独立重推无误。**问题不在数学，在渲染**（见 F1）。
- **播放池记账正确**：三个集合按构造互斥，`releaseAll()` 恰好各释放一次，`release()` 幂等且对未知 key 安全，`acquire()` 不会返回已销毁实例，`trim()` 不会触碰 `owned`，`idle` 不会超过 `maxSize`。唯一缺陷是 R12 的上限语义。
- **`@TransactionalEventListener(AFTER_COMMIT)` 语义正确**：回滚则不投递且无残留行；监听器异常被 `runCatching` 包住不影响响应；`fallbackExecution=false` 导致的「非事务下静默丢弃」当前不可达（`publish` 只由 controller 经代理调用，无自调用）。已 grep 确认队列的生产者只有 after-commit 投递器与兜底任务。
- **`UserRepository` 的原子自增用法正确**：`flushAutomatically` 保证了待插入的 `UserFollow` 先落库再执行批量 UPDATE，`clearAutomatically` 之后没有任何代码再读该实体。
- **定时任务不会互相重叠**：未配置 `spring.task.scheduling.pool.size`，Spring Boot 用单线程调度器。需要知道的是副作用：3 点的对账会独占该线程，阻塞其余定时任务（真实的重叠在调度线程与 AMQP 监听线程之间，即 R2）。
